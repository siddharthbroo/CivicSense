# CivicSense — Personal Project Notes

## BUG FIX 1: Incident Location Map Picker

**What was the problem?**
Clicking "View on Map" opened Google Maps instead of letting users select the incident location inside the complaint form.

**What did we change?**
We added an interactive map picker where users can select a location and click "Confirm Location".

**Why did we do this?**
The complaint must store the exact location where the civic issue occurred, not just the user's current GPS location.

**How does it work now?**
Users select a point on the map and confirm it. The selected latitude and longitude are filled into the complaint form. GPS location is only a suggestion until the user confirms it.

**Interview explanation:**
"I fixed the incident location selection flow so users can select and confirm the exact complaint location on a map. This prevents the system from automatically treating the user's current GPS location as the incident location."

## BUG FIX 2: NoClassDefFoundError in Risk Assessment (M5)

**What was the problem?**
The backend crashed at M5 Risk Assessment with `NoClassDefFoundError: RiskAssessmentServiceImpl$1`.

**What did we change?**
We identified that stale incremental class compilation deleted the synthetic inner class generated by `javac` for enum `switch` statements. We performed a clean backend build with `./mvnw clean compile` and added a focused unit test.

**Why did we do this?**
In Java, switching on an enum creates an inner synthetic helper class (`$1`). An incomplete or stale build can leave the main class behind while dropping the inner class, causing runtime crashes when the switch is evaluated.

**How does it work now?**
The clean compilation regenerated `RiskAssessmentServiceImpl$1.class` in `target/classes`. All severity levels now evaluate properly without runtime classloader errors.

**Interview explanation:**
"I resolved a `NoClassDefFoundError` in the risk assessment pipeline caused by a stale compiler build mismatch, where the synthetic helper class generated for enum switch mapping was missing from the classpath. A clean Maven recompilation restored the complete class set and resolved the crash."

## DECISION 1: Location Validation & Service Area Integrity (Step 1)

**What was the problem?**
Users could input invalid coordinates, transposed latitude/longitude, locations in water bodies, or locations completely outside CivicSense's supported service area (Delhi NCR).

**What did we change?**
We added coordinate validation on both the frontend and backend:
1. Checked boundaries for Delhi NCR (latitude 28.20–29.00, longitude 76.70–77.60).
2. Detected swapped coordinates (latitude in longitude field) and offered a one-click correction suggestion.
3. Detected water bodies (lakes and Yamuna River) and showed an advisory for road/infrastructure issues.
4. Disabled the "Confirm Location" button on the map picker whenever coordinates are invalid or outside Delhi NCR.
5. Added backend validation in `LocationValidationService` to prevent invalid submissions via API.

**Why did we do this?**
A civic system only serves designated municipal jurisdictions. Preventing invalid or out-of-jurisdiction coordinates upfront protects backend processing, avoids routing complaints to nonexistent wards, and improves data quality before AI processing (M3/M4/M5).

**How does it work now?**
When a user moves the pin on the map or enters coordinates manually:
- If the location is outside Delhi NCR, a clear error appears and confirmation is blocked.
- If coordinates are swapped, a suggestion banner appears asking "Did you mean..." with a button to flip them.
- If placed in a water body for a road issue, an advisory reminder asks to verify if it's on a bridge.
- The backend performs the same check before saving any complaint.

**Interview explanation:**
"I implemented geographic boundary and coordinate integrity checks across both frontend and backend. The system enforces Delhi NCR boundaries, catches swapped coordinates with automatic suggestions, warns users if infrastructure pins fall in water bodies, and validates coordinates before complaint creation to ensure data reliability."

## DECISION 2: Image Integrity, Multimodal Moderation & Fail-Safe Quarantine (Step 2)

**What was the problem?**
Users could upload corrupted files, spoofed extensions, or inappropriate imagery (such as pornography, hate symbols, or doxxing). Furthermore, public cloud images could leak private user EXIF metadata (exact home GPS, timestamp).

**What did we change?**
1. **File Integrity Verification**: Enforced format restrictions (JPG, PNG), 10MB limits, magic number byte inspection, and image decodability.
2. **Civic-Aware Multimodal Moderation**: Reused Gemini to pre-screen images before permanent ImageKit storage. Designed prompt rules that strictly prohibit CSAM, explicit nudity, hate group symbols, and doxxing, while explicitly protecting legitimate unpleasant civic photographs (sewage, garbage dumps, dead stray animals, burnt debris, potholes).
3. **Fail-Safe Quarantine**: If the moderation service is unreachable or uncertain, the image is quarantined for review rather than blindly trusted or sent to public storage.
4. **EXIF Stripping**: Private EXIF metadata is extracted server-side as an intake hint, but stripped before uploading to public cloud storage.
5. **Submit Blocking**: Disabled the frontend Submit button while screening is active or if prohibited content is detected, with immediate inline explanations.
6. **Backend Enforcement**: Complaint creation strictly validates image bytes prior to storage and throws descriptive errors to prevent API bypass.

**Why did we do this?**
A public civic platform must remain safe for municipal workers and the community without rejecting genuine civic issues simply because they look unpleasant. Pre-moderating image bytes before storage saves cloud storage costs and prevents prohibited content from entering public view.

**How does it work now?**
When an image is attached, the frontend runs format and size checks, then requests a real-time safety pre-screen. If prohibited, an inline badge explains the policy violation and locks the Submit button until removed. Upon complaint creation, the backend validates the image again, strips EXIF before uploading to ImageKit, and safely quarantines uncertain files if moderation is offline.

**Interview explanation:**
"I designed a multi-layer image validation and content moderation pipeline using Gemini. It validates magic bytes, strips sensitive EXIF GPS data before public storage, and distinguishes prohibited content like hate symbols from legitimate unpleasant civic photos like sewage or roadkill. A fail-safe quarantine ensures unmoderated images are never publicly published if AI moderation is offline."

## DECISION 3: Image Relevance Validation (Combined with Moderation)

**What was the problem?**
A user could upload a cat photo for a ROAD_DAMAGE complaint. The old moderation only checked for safety (nudity, hate, etc.), so the cat photo passed as "safe" and the Submit button became enabled — even though the image is completely unrelated to the complaint.

**What did we change?**
We extended the same Gemini moderation call to also check if the image is relevant to the complaint type and description. We combined safety and relevance into a single API call.

**Why did we do this?**
Using two separate AI calls would double latency and cost. By combining them in one prompt, we get both answers together. Also, a civic system should only accept evidence that actually relates to the reported problem.

**How does it work now?**
When a photo is attached, the backend asks Gemini: "Is this image safe AND relevant to this type of civic complaint?" The answer can be:
- **RELEVANT** or **POTENTIALLY_RELEVANT** → photo is accepted.
- **UNRELATED** (e.g. a cat for a road damage complaint) → photo is rejected with a red error badge. Submit is blocked until the user removes or replaces the photo.
- **UNCERTAIN** → photo is quarantined. Submit is blocked until the photo is removed.

The frontend auto-re-checks when the user changes the photo, category, or description. Removing the photo always allows text-only submission.

**Interview explanation:**
"I extended the image moderation pipeline to also check relevance in the same Gemini multimodal call. For example, a cat photo for a road damage complaint is flagged as 'unrelated' and blocks submission. This prevents low-quality evidence from entering the system while keeping the same latency and cost as before, since both checks run in one API call."

## DECISION 4: EXIF Provenance & Image Reuse Detection (Step 3)

**What was the problem?**
Users could download photos from the internet, reuse the same photo for complaints in completely different neighborhoods (e.g., claiming a pothole in Rohini using a photo taken in Noida), or repeatedly upload duplicate photos. Additionally, raw EXIF metadata could leak private citizen location data if published directly to public cloud storage.

**What did we change?**
1. **Server-side EXIF Extraction & Privacy**: Extracted camera GPS and timestamp on the backend as supporting provenance signals. When EXIF GPS exists, we calculate its distance to the citizen-confirmed pin. If greater than 500m, an `EXIF_LOCATION_MISMATCH` signal is flagged. Before uploading to public ImageKit storage, EXIF is stripped to protect user privacy. Raw EXIF is never returned in public API responses.
2. **Cryptographic & Perceptual Hashing**: Generated SHA-256 (byte-exact match) and dHash (64-bit difference perceptual hash) for uploaded photos in pure Java without extra heavy dependencies.
3. **Contextual Reuse Rules**:
   - Same image, same citizen, same spot (<= 150m): `RESUBMISSION` (follow-up/retry; not fraud).
   - Same image, different citizens, same spot (<= 150m): `COMMUNITY_SHARED` (neighbours reporting the same issue with a shared photo; not fraud).
   - Same image, different locations (> 150m): `DIFFERENT_LOCATION` (suspicious signal).
   - Same image reused across 3+ distinct locations: `MULTI_LOCATION_DISPERSED` (strong suspicious signal).
4. **Non-Blocking Safety Principle**: Missing EXIF is completely normal (many phones or chat apps strip it) and is never treated as suspicious. Suspicious image reuse or EXIF conflicts flag a complaint for field verification in the Verification Gate, but NEVER automatically reject a complaint or reduce its priority.

**Why did we do this?**
Civic systems must catch photo recycling across distant neighborhoods without punishing genuine citizens who resubmit complaints or neighbors who share photos in local WhatsApp groups. Missing EXIF must never block a complaint.

**How does it work now?**
When a complaint is submitted with an image:
- SHA-256 and dHash are calculated and compared against existing complaint images.
- If reuse is detected, the location distance and user IDs determine whether it's a resubmission, community-shared evidence, or suspicious cross-location reuse.
- EXIF metadata is extracted, checked against the confirmed incident location, and stripped before public cloud storage.
- If suspicious signals exist, the Verification Gate marks `verificationRequired = true` for field inspection, while keeping the original complaint priority intact.

**Interview explanation:**
"I built a lightweight image provenance and reuse detection engine using SHA-256 and perceptual difference hashing (dHash) in pure Java. It distinguishes legitimate community photo sharing from suspicious cross-location reuse where someone uses the same pothole photo across different wards. Suspicious signals route complaints to the verification queue without ever rejecting complaints or lowering priority, and server-side EXIF is stripped before cloud storage to protect citizen privacy."

## DECISION 5: End-to-End Validation & M2–M5 Pipeline Integration (Step 4)

**What was the problem?**
We had separate validation modules (coordinates, image safety/relevance, EXIF distance, and image reuse) that needed to integrate cleanly with our multi-stage AI complaint intake pipeline (M2 Ward Resolution, M3 Gemini Analysis, M4 Duplicate Detection, and M5 Risk Assessment) without creating conflicts, without blocking valid text-only complaints, and without accidentally downgrading complaint priorities.

**What did we change?**
1. **Intake Gatekeeping**: Enforced authoritative backend coordinate validation and image safety/relevance blocking upfront. Out-of-service-area locations and prohibited or clearly unrelated images are immediately rejected with clear errors.
2. **Text-Only Complaint Guarantee**: Photos remain strictly optional. If no photo is provided, the intake bypasses cloud storage and image hashing, assigns Evidence Level E0, and allows normal AI processing and dispatch.
3. **Suspicious Findings vs. Hard Rejections**: Separated fatal validation errors from suspicious provenance signals. If an image has an EXIF location mismatch (>500m) or suspicious cross-location reuse, the complaint is still accepted and submitted normally (`status = SUBMITTED`).
4. **Verification Gate Routing**: The suspicious flags are routed to M5's Verification Gate, which marks `verificationRequired = true` for field officer review.
5. **Priority & Dispatch Preservation**: The complaint priority is strictly computed from the weighted risk formula and is never downgraded due to suspicious signals. Urgent complaints proceed to dispatch without delay.

**Why did we do this?**
In civic governance, we must never delay a critical hazard (such as an open manhole or fallen power line) just because the attached photo was reused or taken from a distance. Critical complaints must dispatch immediately while queuing for verification.

**How does it work now?**
- Invalid coordinates or bad/unrelated photos are rejected at intake.
- Valid complaints (with or without a photo) flow through M2 ward mapping, M3 AI classification, M4 duplicate clustering, and M5 risk scoring.
- If suspicious EXIF or reuse is detected, M5 flags `verificationRequired = true` for officer inspection, but preserves the original high/critical priority and submits the complaint cleanly.

**Interview explanation:**
"I integrated the validation rules with the M2–M5 complaint pipeline. Invalid locations and prohibited/unrelated photos are blocked at the door, but suspicious provenance signals like EXIF distance conflicts or cross-ward photo reuse never reject a complaint or reduce its priority. Instead, they flag the complaint for field officer inspection in the M5 verification gate while letting urgent dispatches proceed immediately."




## DECISION 6: Zone & Ward Foundation for Officer Module (Step 1)

**What was the problem?**
The previous zone/ward implementation made flawed real-world municipal assumptions:
1. It assumed every ward must belong to an administrative zone (not true for many municipalities that have no intermediate zones).
2. It assumed ward numbers are globally unique (in reality, ward numbers like "Ward 1" repeat across different municipal corporations).
3. It required non-null bounding box coordinates on all wards, forcing developers to fabricate fake spatial boxes for official wards before GIS boundary data was surveyed.
4. It had no boundary provenance tracking to distinguish surveyed municipal boundaries from provisional testing boxes or wards without boundary data (`NO_BOUNDARY`).
5. There was no protection against accidental overwriting or silent downgrading of verified municipal GIS delimitation data.

**What did we change?**
1. **Verifiable Municipal Foundation**: Decoupled `AdministrativeZone` and `AdministrativeWard` as distinct domain concepts. Made parent zone optional/nullable (`zone_id` nullable in database).
2. **Authority Scoping**: Added `municipality` (e.g. "Municipal Corporation of Delhi (MCD)", "Ghaziabad Nagar Nigam") to both Zone and Ward, scoping code and ward number uniqueness per municipal authority.
3. **Boundary Provenance**: Added `BoundaryProvenance` enum (`VERIFIED_BOUNDARY`, `PROVISIONAL_BOUNDS`, `NO_BOUNDARY`). Kept bounding box coordinates nullable so official wards without GIS boundaries can exist safely without fake data.
4. **Boundary Integrity & Overwrite Protection**: Built `AdministrativeGeographyService` with strict coordinate range checking (`[-90, 90]`, `[-180, 180]`, `min <= max`, centroid inside box), forbidden fake coordinates for `NO_BOUNDARY`, and an explicit `forceBoundaryOverwrite` requirement before any `VERIFIED_BOUNDARY` can be altered or downgraded.
5. **Spatial Resolution Compatibility**: Updated `AdministrativeWardRepository.findWardsContainingPoint` with `LEFT JOIN FETCH w.zone` so direct municipal wards without a parent zone can also be resolved, and prioritized `VERIFIED_BOUNDARY` over `PROVISIONAL_BOUNDS` during pin resolution in `GeographicHierarchyService`.
6. **Authorized Admin API**: Exposed secured endpoints under `/api/v1/admin/geography/**` where read operations are authenticated and mutation operations (POST/PUT) require `@PreAuthorize("hasRole('ADMIN')")`.

**Why did we do this?**
In public sector civic infrastructure, administrative boundaries are established by statutory delimitation orders. A solid domain model must respect how municipalities actually function rather than relying on fabricated coordinates or naive global uniqueness assumptions.

**How does it work now?**
- Municipalities can register zones and wards with or without an intermediate zone layer.
- Official wards can be created as `NO_BOUNDARY` until official GIS files are ready; any attempt to attach fake coordinates to `NO_BOUNDARY` is blocked.
- Wards with `VERIFIED_BOUNDARY` cannot be silently overwritten or downgraded without explicit admin confirmation (`forceBoundaryOverwrite = true`).
- Map pin resolution continues to resolve confirmed coordinates seamlessly, giving precedence to verified boundaries.

**Interview explanation:**
"I established the Zone and Ward domain foundation for the upcoming Officer Module. Rather than assuming all wards belong to zones or that ward numbers are globally unique, I modeled them around verifiable municipal structures: wards can exist directly under a municipality without a parent zone, ward numbers are scoped per municipal authority, and boundary coordinates are nullable with explicit provenance tracking (`VERIFIED_BOUNDARY`, `PROVISIONAL_BOUNDS`, `NO_BOUNDARY`). I also implemented protection against silent boundary overwrites, forbidding fake coordinates for wards without GIS data, and secured administrative management endpoints with Spring Security method-level authority."

## DECISION 7: Officer Identity & Profile Foundation (Step 2A)

**What was the problem?**
We needed an official officer identity and profile foundation without compromising our existing security and authentication mechanisms.
Flawed approaches to avoid:
1. Creating a separate authentication entity or duplicate login/password table for officers.
2. Allowing citizens to self-register as officers or escalate their roles via public endpoints.
3. Automatically granting operational officer permissions merely because an officer profile record exists.
4. Hardcoding officer assignments directly to spatial ward entities or complaints.

**What did we change?**
1. **Reused Existing User Authentication Principal**: Linked `OfficerProfile` 1:1 with `User` (`@OneToOne @JoinColumn(name = "user_id", unique = true)`). Authentication, password hashing (BCrypt), mobile verification, and JWT issuance remain centralized in `User` and `AuthService`.
2. **Dedicated Officer Domain Model**: Created `OfficerProfile` with `employeeCode`, `designation`, `department`, `governmentEmail`, `municipality`, `active`, and `OfficerVerificationStatus`.
3. **Municipal Scoping**: Scoped employee code uniqueness per municipal corporation (`uk_officer_muni_code(municipality, employee_code)`).
4. **Verification Lifecycle**: Implemented `OfficerVerificationStatus` with states `PENDING_VERIFICATION`, `VERIFIED`, `REJECTED`, and `SUSPENDED`.
5. **Decoupled Verification from Role Granting**: Initial officer provisioning creates a profile in `PENDING_VERIFICATION` without granting `ROLE_OFFICER`. Only an administrator's transition to `VERIFIED` synchronizes `ROLE_OFFICER` onto the `User`. Transitioning to `SUSPENDED` or `REJECTED` immediately revokes `ROLE_OFFICER`.
6. **Secured Administrative APIs**: Exposed provisioning and verification endpoints under `/api/v1/admin/officers/**` guarded by `@PreAuthorize("hasRole('ADMIN')")`, and self-profile retrieval under `/api/v1/officers/me` guarded by `@PreAuthorize("hasRole('OFFICER')")`.

**Why did we do this?**
In government systems, officer identity verification is an administrative HR process distinct from public citizen registration. By separating authentication (`User`) from officer credentials (`OfficerProfile`) and synchronizing Spring Security authorities dynamically with the officer's verification status, we prevent unauthorized access while maintaining loose coupling.

**How does it work now?**
- Administrators provision officer profiles linked to existing users.
- The profile starts in `PENDING_VERIFICATION` (not operationally authorized; no `ROLE_OFFICER`).
- When an administrator verifies official credentials, status moves to `VERIFIED` and `ROLE_OFFICER` is added to the user's authorities.
- If an officer is suspended or rejected, `ROLE_OFFICER` is immediately revoked.
- Public citizen registration continues to strictly assign only the `CITIZEN` role.

**Interview explanation:**
"I implemented Step 2A of the Officer Module by establishing the OfficerProfile domain foundation. Rather than creating a duplicate authentication system, I reused the existing User entity as the security principal and linked it 1:1 to OfficerProfile. I introduced a verification lifecycle (`PENDING_VERIFICATION`, `VERIFIED`, `REJECTED`, `SUSPENDED`) where `ROLE_OFFICER` is only synchronized when an administrator explicitly verifies the officer's credentials, and is immediately revoked upon suspension. All provisioning is restricted to administrators, guaranteeing zero role escalation through public citizen registration."
